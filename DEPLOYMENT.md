# Развёртывание и проверка

## Текущая схема

Приложению нужен долгоживущий Node-процесс: очереди запускаются из Next.js instrumentation. Материалы находятся в PostgreSQL, а master key для зашифрованных подключений находится на постоянном томе сервера. Статический GitHub Pages и обычные короткоживущие serverless-функции не являются полноценным развёртыванием этого проекта.

Ниже описан один сервер с Docker Compose и собственным доменом. Требуются Docker Engine с Compose, DNS A/AAAA на сервер, открытые 80/443, достаточное дисковое место для PostgreSQL и резервных копий. Пароли, БД, ключи и пользовательские файлы не загружаются в GitHub.

## Подготовка

1. На сервере клонировать репозиторий и создать `.env.production` по `.env.production.example` (`chmod 600 .env.production`). Указать разные для каждого окружения сильные секреты. `POSTGRES_PASSWORD` и пароль в `DATABASE_URL` должны совпадать; в URL нужны URL-encoded символы. `APP_DOMAIN` должен совпадать с HTTPS host в `APP_ORIGIN`. Оставить `ENABLE_LOCAL_SEED=false` и `ASSESSMENT_ENVIRONMENT=standard`.
2. Проверить, что DNS уже ведёт на этот сервер. Затем выполнить:

   ```sh
   docker compose --env-file .env.production -f compose.yaml -f compose.public.yaml up -d --build
   docker compose --env-file .env.production -f compose.yaml -f compose.public.yaml ps
   curl -fsS https://YOUR_DOMAIN/api/health
   ```

   Caddy получает TLS-сертификат для домена; приложение и PostgreSQL находятся во внутренней сети Compose. Порт приложения дополнительно открыт только на loopback сервера для локального контроля. Команда старта сначала выполняет `prisma migrate deploy`, затем запускает Next.js на `0.0.0.0:3000`. В первый запуск пользовательские учётные записи не создаются seed-скриптом.
3. Создать **первого** сотрудника без публичного seed. Команда принимает пароль только через stdin, работает один раз и откажется при уже существующем сотруднике:

   ```sh
   read -r -s -p 'Пароль первого сотрудника: ' INITIAL_STAFF_PASSWORD
   printf '\n'
   printf %s "$INITIAL_STAFF_PASSWORD" | docker compose --env-file .env.production -f compose.yaml -f compose.public.yaml exec -T app npm run staff:bootstrap -- staff@your-domain.example 'Имя Фамилия'
   unset INITIAL_STAFF_PASSWORD
   ```

   Используйте личный адрес уполномоченного сотрудника и пароль от 14 символов. Скрипт не подтверждает email автоматически; владение адресом и право сотрудника проверяются организационно до выдачи доступа. Не запускать скрипт на БД с уже существующими сотрудниками.
4. Открыть `/`, зарегистрировать тестового кандидата, проверить черновик и отправку на специально подготовленных данных. Войти сотрудником и пройти загрузку материала, чтение собственного файла, решение, доступ к World после подачи и сохранение после обновления. `/api/health` показывает только доступность БД, не проверяет эти пользовательские сценарии.

Для закрытого стенда без публичного домена используйте только `compose.yaml` и локальный порт; `APP_ORIGIN` должен быть точным доступным origin, `COOKIE_SECURE=false` допустим **только** для HTTP на локальном тесте. WebAuthn требует совпадения origin и RP ID. Не объявляйте вход с физического телефона проверенным по локальному тесту.

## Обновление и восстановление

Перед обновлением сделать проверяемую резервную копию PostgreSQL и сохранить отдельно том `app_secrets`. Секретный том и БД образуют пару: потеря master key лишает доступа к сохранённым OpenAI/Google credentials. После бэкапа получить новый коммит и повторить `docker compose ... up -d --build`; миграции добавочные. Не запускать `db:seed`, `setup`, `showcase:*` или тесты против рабочей БД. Восстановление проверять на отдельном окружении до инцидента. Не копировать `.env.production` в поддержку или CI-логи.

Проверка после обновления: `docker compose ... ps`, `/api/health`, открытие лендинга, вход/выход, приватный файл, состояние фоновой очереди и один разрешённый тестовый сценарий World. При ошибке сначала смотреть обезличенные логи контейнера и статус миграций; не публиковать payload заявки. Критические сигналы для мониторинга: 503 health, перезапуски процесса, свободное место БД, старые задания очереди, ошибки публикации Calendar. Для долгой эксплуатации нужны политика хранения, backup retention, мониторинг и утверждённые права сотрудников.

## Внешние подключения

OpenAI настраивается владельцем через `/settings/openai` с действующим согласием и бюджетом. Не размещайте ключ в клиенте или `.env.production`. Google Meet требует OAuth Web client, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` и redirect URI `https://YOUR_DOMAIN/api/google/callback`; сотрудник подключает календарь в `/settings/calendar`. Без этих настроек локальные функции приложения работают, а автоматические внешние вызовы и настоящая Meet-ссылка не подтверждены. Учебный seed создаёт известные пароли только на loopback-БД и запрещён для публичной среды.

## Проверка поставки без облачного сервера

`npm ci`, `npm run typecheck`, `npm run lint`, `npm run quality:check`, `npm run build` проверяют код и production-сборку. Полный `npm test` требует отдельной локальной базы и запущенного собранного приложения с тем же `DATABASE_URL` и `TEST_ORIGIN`. CI использует изолированный PostgreSQL и локальный транспорт. Эти проверки не заменяют внешний HTTPS, восстановление из бэкапа, реальный OAuth/Meet и браузерный smoke test на развернутом домене.
